# تصميم استخراج حقول الفواتير

الحالة: مقابلة تصميم جارية. آخر تحديث: 4 أكتوبر 2026.

## الفهم المؤكد

- المنتج يعالج فواتير عربية وإنجليزية، بصور أو PDF، ويحوّل المحتوى إلى حقول منظمة.
- الحقول الحالية: رقم الفاتورة، اسم المورد، التاريخ، الإجمالي، مبلغ الضريبة، العملة.
- نحو 160 قالبًا يصف تنوع المدخلات. التعرف على القالب ليس مطلبًا للمنتج.
- المستخدم اختار LightOnOCR للقراءة بدل Docling.
- النموذج المحلي المتاح بحسب المستخدم هو Qwen3.8-27B.
- المطلوب نظام صالح للإنتاج، مع اهتمام بالدقة واستهلاك موارد التشغيل المحلي.
- الحجم المتوقع بالآلاف، لكن الفترة الزمنية وعدد الصفحات ومواصفات السيرفر لم تتحدد.

## الاتجاه المقترح

قراءة المستند، ثم استخراج عام إلى schema واحدة، ثم تحقق وتسليم النتيجة. يمكن بدء الاستخراج بالنموذج المحلي وإجراء تحسينات التكلفة بناءً على القياسات. هذا اتجاه للنقاش، وليس قرار نشر أو اعتماد آلي نهائي.

المصطلحات المعتمدة في [CONTEXT.md](../CONTEXT.md). المصادر والبدائل في [مذكرة البحث](invoice-extraction-research.md).

## شجرة القرارات

### الجولة الأولى: قرارات مستقلة مفتوحة

1. تسليم النتائج: شاشة وتصدير، أم API لنظام آخر؟
2. النتيجة الناقصة أو الملتبسة: مراجعة مع الاحتفاظ بالحقول الصحيحة، أم رفض كامل؟
3. وحدة الإدخال: فاتورة واحدة قد تمتد عبر صفحات لكل ملف، أم عدة فواتير مستقلة داخل الملف نفسه؟
4. معنى الإجمالي: الإجمالي شامل الضريبة، أم المبلغ المستحق بعد الدفعات، أم كلاهما؟

### فروع تنتظر القرارات السابقة

- شكل تجربة المستخدم أو عقد API وصلاحياته بحسب طريقة التسليم.
- دورة المراجعة والتصحيح وحدود الاعتماد بحسب سياسة النتائج.
- حدود الفواتير وتقسيم الملفات بحسب وحدة الإدخال.
- تعريف schema النهائي ومعالجة الغياب والالتباس بحسب معاني الحقول.
- معيار قبول الدقة والمدة المطلوبة لمعالجة الدفعات قبل تقدير السعة.

تسجل الإجابات عند وصولها؛ التوصيات المقدمة أثناء المقابلة تظل مقترحات حتى يختارها المستخدم.

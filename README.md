# مِعيار — Invoice Studio

تطبيق محلي لقراءة الفواتير العربية والإنجليزية ومراجعتها. واجهة React تعرض الصفحة الأصلية بجانب قراءة LightOnOCR المنسقة والجداول، ثم الحقول والبنود المستخرجة محليًا بـRegex وقارئ الجداول. يمكن مقارنة النتائج بقراءات OpenAI المحفوظة. القرار النهائي للمستخدم.

## التشغيل على Windows

المتطلبات: Python 3.11 أو أحدث وNode.js 22.12 أو أحدث. إعداد Python في بيئة افتراضية باستخدام uv الموجود على الجهاز:

```powershell
uv venv .venv --python 3.12
uv pip install --python .venv/Scripts/python.exe -r requirements.txt
npm ci
Push-Location frontend
npm ci
Pop-Location
```

إذا لم يكن `.env` موجودًا، انسخ `.env.example` إليه. الافتراضي `EXTRACTION_METHOD=regex` يعمل محليًا دون مفتاح أو اتصال تحليلي خارجي. لتفعيل OpenAI صراحةً غيّرها إلى `openai` وضع مفتاحك أمام `OPENAI_API_KEY` في الملف المحلي؛ لا تضعه في كود الواجهة أو المستودع. الافتراضي `OPENAI_MODEL=gpt-6-luna`، ويمكن تغيير النموذج و`OPENAI_REASONING_EFFORT` بحسب النماذج المتاحة لحسابك. اترك effort فارغًا للنماذج التي لا تقبله.

```powershell
npm run dev
```

افتح http://127.0.0.1:5173. تعمل API على المنفذ 8000. مشغّل npm يستخدم Python من `.venv` عند وجودها، وإلا يستخدم Python المتاح في PATH. شغّل نسخة واحدة فقط من backend؛ هي التي تملك نموذج OCR والطابور. أعد تشغيل التطبيق بعد تعديل `.env`.

للتشغيل المنفصل:

```powershell
node scripts/python.mjs -m backend
npm --prefix frontend run dev
```

أوزان LightOnOCR-2-1B وllama.cpp موجودة في `.local/lightonocr/` من التجربة السابقة، ويستخدمها التطبيق مباشرة. لا يحتاج التطبيق لمسار صورة الفاتورة القديمة أو ملفات نتائجها. إذا لم تتوفر الأوزان، راجع `experiments/lightonocr/README.md` وإعداد التنزيل هناك؛ عند نقل المشروع ضع أوزان النص Q8_0 والرؤية F16 ونسخة CPU من llama.cpp في البنية نفسها، أو حدد `LIGHTONOCR_BASE_URL` لخدمة OCR محلية موجودة.

## الفلو والمراجعة

1. ارفع صور PNG/JPEG/WEBP أو PDF. كل ملف فاتورة مستقلة؛ حتى 10 ملفات بالدفعة و20MB و10 صفحات لكل ملف، قابلة للتغيير من `.env`.
2. تعالج الوثائق بالتتابع. يبقى LightOnOCR محمّلًا، وتظهر الصفحة الحالية والقراءة أثناء المعالجة. النموذج يعمل على CPU في هذا الجهاز؛ قراءة الفاتورة اليدوية السابقة استغرقت نحو 3.5 دقائق.
3. يقارن المستخدم الأصل بقراءة OCR المرتبة أو النص الخام. هذه القراءة تظل محفوظة حتى عند فشل تحليل OpenAI.
4. يستخرج backend الحقول بالقواعد والبنود من HTML أو Markdown محليًا. القيم المتعارضة والتواريخ الغامضة تبقى فارغة. لا يصنّف Regex الأصناف أو يعطي نسبة ثقة؛ يختار المستخدم التصنيف. إذا ضُبط `EXTRACTION_METHOD=openai` صراحةً، يُرسل نص OCR فقط إلى OpenAI؛ إعداد `store=False` لا يعني انعدام كل احتفاظ لدى مزود API.
5. يمكن تصحيح البيانات والبنود أو إضافة وحذف بند، وتغيير التصنيف. القراءة الأصلية واقتراح النموذج لا يتغيران. اعتماد البيانات الناقصة أو التناقضات يحتاج إقرارًا بالتنبيهات.
6. يُحفظ ناتج الاستخراج والتصحيح النهائي ومصدر المراجعة ووقتها والإقرار منفصلًا. زر «استخراج بـRegex» في الوثائق القديمة يعيد استخدام قراءة الصفحات ويحفظ نتيجة مقارنة منفصلة، مع بقاء اقتراح النموذج السابق. زر «إعادة الاستخراج بـRegex» يشغّل الإصدار الحالي على النص المحفوظ، ويحفظ سجل المقارنات السابقة ومعرّف النتيجة التي راجعها المستخدم. التغيير اليدوي لا يعيد تصنيف الفاتورة آليًا.

التصنيفات الأربعة: أجهزة كمبيوتر، جوالات وأجهزة لوحية، طابعات ومعدات مكتبية، ملحقات تقنية. الفواتير خارج النطاق تُراجع ويمكن اعتمادها بلا تصنيف. تقدير الثقة ليس قياسًا لدقة النموذج؛ جميع الفواتير تحتاج مراجعة بشرية، حتى لو تجاوزت الثقة 0.75.

## البيانات والأخطاء

SQLite والملفات والمخرجات والسجل المحلي محفوظة في `.local/invoice-app/`، ومهملة من Git. احتفظ بهذا المجلد كاملًا عند أخذ نسخة احتياطية. لا توجد بيانات نموذجية أو fallback وهمي داخل التطبيق.

- غياب المفتاح عند اختيار `openai`: يكتمل OCR ويظهر تنبيه التحليل. اضبط `.env` وأعد تشغيل التطبيق ثم اختر «إعادة المحاولة»؛ لا يتكرر OCR المكتمل.
- فشل صفحة: تبقى الصفحات المكتملة، ويعاد فقط ما لم يكتمل. لا تُحلل فاتورة بصفحات فاشلة على أنها مكتملة.
- قراءة مقطوعة عند حد الرموز: تظهر كفشل مع القراءة الجزئية؛ ارفع `LIGHTONOCR_MAX_TOKENS` والسياق حسب الموارد ثم أعد التشغيل والمحاولة.
- إعادة تشغيل التطبيق أثناء المعالجة: تصبح الوثيقة المنقطعة قابلة لإعادة المحاولة؛ تبقى الوثائق المعتمدة محفوظة.
- `.local/invoice-app/lightonocr-server.log` يحتوي سجل OCR. تفاصيل الوثيقة تعرض النص المرسل للتحليل والنتيجة الأصلية والأزمنة دون مفتاح API.

خدمة محلية لمستخدم واحد دون تسجيل دخول. ليست إعداد نشر عام أو معالجة متوازية لآلاف الوثائق. لا توجد RAG أو Agents أو تدريب أو تصنيف لقوالب الفواتير.

## الاختبارات والبناء

```powershell
npm test
npm run build
npm run test:e2e
```

اختبارات backend والواجهة تستخدم بدائل معلنة للخدمات. اختبارات Playwright تشغل API اختبار مستقلة على 8001 وواجهة على 5174 وتخزن بياناتها في `.local/e2e-runs/`، باستخدام Microsoft Edge المثبت على Windows. لا تؤثر على بيانات التطبيق الحقيقي. يمكن تغيير `channel` في إعداد Playwright لجهاز لا يحتوي Edge.

الاختبارات تثبت الفلو والحفظ والتحقق والنقل وبنية المخرجات؛ أمثلة التصنيف ذات النتائج المحددة ليست تقييم دقة لنموذج OpenAI الحقيقي. اختبار OpenAI الحقيقي يحتاج مفتاح API وصلاحية النموذج. تم اختبار LightOnOCR وOpenAI الحقيقيين على الفاتورة المرفقة، واختُبر Regex v2 على القراءات الأربع المحفوظة. هذه أمثلة تطوير وليست تقييم دقة مستقلًا على الفواتير الجديدة. راجع docs/app-verification.md وdocs/regex-extraction.md.

واجهة API موثقة على http://127.0.0.1:8000/docs. رفع الملفات يرجع 202 ومعرّفات الوثائق، وتُقرأ النتائج لاحقًا. للاستيراد أو الربط راجع نماذج Pydantic في backend؛ `ai_proposal` اسم قديم في عقد API يحتفظ بنتيجة المستخرج الأساسي، سواء كان Regex أو OpenAI؛ `analysis.method` يحدد المصدر. `regex_result` نتيجة المقارنة المحلية، و`review_source` يحدد النتيجة التي تمت مراجعتها. `classification.key` اقتراح التصنيف، و`final_classification` قرار المستخدم.

مراجع تكامل OpenAI: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) و[النموذج الافتراضي GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).
